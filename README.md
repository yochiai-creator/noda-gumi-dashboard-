### ファイル名・配置についての重要な注意

GASは**全ファイルが同一のグローバルスコープで、エディタのファイル順に評価される**ため、
同名関数を複数ファイルに置くと「最後に評価された定義」が勝つ。
実際に `noda_yard_extras.js` の8関数が `noda_yard_edit_engine.js` の定義を上書きし、
PDF検索の高速化（キャッシュ化）が効かなくなっていた（2026/09に発覚・修正）。

**関数を追加するときは既存ファイルに追記し、同名関数を2箇所に置かないこと。**
また、ファイルを増やす・リネームするときは、本番プロジェクト側のファイル名と
必ず一致させること（別名で`clasp push`すると重複定義が発生する）。

### 配車表と出荷指図書の紐づけ（2026/09）

配車の「日」表示で、そのトラックがどの出荷指図書のものかを出している。
拾い方は2通りあり、画面でも見分けが付くようにしてある。

| 出どころ | 条件 | 画面 |
| --- | --- | --- |
| 依頼ナンバー | マスの中身が数字と矢印だけ（`↓60688` `30412,30458→ 30413`） | 青ベタのボタン |
| 行き先の住所 | マスが住所（`熊本県山鹿市`）で、出荷希望日と市区町村が一致 | 青枠のボタン＋「行き先と出荷日から推定」 |

住所での突き合わせには、指図書PDFから読んだ**出荷先の住所**が要る。
出荷先コードと住所は1対1なので、`実績` シートの `住所 / 都道府県 / 市区町村` の
3列に**出荷先コードごとに1行だけ**入れてある。埋めるのは
`shipact_fillDestAddresses_()`（夜間の `harvestDailyData` から残り時間ぶんだけ）。
すぐ効かせたいときは `出荷先の住所を集める()` を手で実行する。

読んでも住所が取れなかった出荷先コードはスクリプトプロパティ
`shipActuals.addrGiveUp` に控えて二度と読み直さない（毎晩同じPDFで足止めされ、
後ろのコードに順番が回らなくなるため）。

注意点：

- 住所からの紐づけは**推定**。市区町村と出荷希望日（前後1日まで）しか見ていない。
  同じ市に同じ日で複数の指図書があれば全部出る。
- 引取（`←`）のマスは住所からは引かない（出荷の指図書ではないため）。
- 指図書PDFのリンクは `実績` シートの `fileId` から作るので、Drive検索が要らず速い。
  シートにまだ無い依頼ナンバーだけ、今までどおり `yard_findOrderPdf_()` で検索する。

**ダッシュボードはこの .xlsm を直接読まない。** 変換だけで十数秒かかるため。

代わりに、別プロジェクト **「アーム出荷明細pdf生成」**
（scriptId `1ZIg-_3vYA1UTAHcUJiHPNtI9m12VTx5MdFJ2WUOJZqt-wrIq1ZAZSl54`）が
.xlsm の更新を15分おきに見て書き出している2つのファイルを使う。
置き場は「①出荷作業用」フォルダ `1-RrriADJSmBt2a7HsYpb_c8TUHHJpxkz`。

| ファイル | 中身 |
| --- | --- |
| `アーム機種別出荷明細_YYYY-MM-DD.pdf` | 落合さんが見ている明細。画面からリンクで開く |
| `arm_pdf_snapshot.json` | `図番\|\|号機` → `{insp, kiki, kishu, spec, ship(ミリ秒), info, dest, is13}` |

`gas/noda_arm_ship.js` はこのJSONを読んで出荷日ごとにまとめるだけ
（Driveのファイルを1つ読むだけなので速い）。

注意点：

- **図番と号機は値の中に無い。** キーが `図番||号機` なので、そこから取り出している。
- PDF生成側が止まるとJSONも古いまま残る。元の .xlsm の更新日時と見比べて、
  JSONのほうが古ければ `stale` を立てて画面に警告を出す。
- 対象は「実行日から31日」。PDF生成側の `DAYS` と合わせてある。
- 元の .xlsm は**ファイル名の日付**で選ぶ（更新日時ではない）。
  古い版を後から開き直すだけで更新日時は新しくなるため、更新日時で選ぶと
  実際に使われた版と食い違う（9月4日の版が9月10日の版より新しく見えていた）。
  PDF生成側の `dateKeyFromName_` と同じ選び方にしてある。
- カードの中に機種別の内訳（`byKind`）を出している。数え方は月別出荷の
  `arm_kindOf_` と同じ（`13ton仕上げ` `13ton ｼｮｰﾄ` → `13ton`）。
  **予定と実績で同じ言葉で数えること。** 違う数え方をすると見比べたときに合わない。
- **トラック（どの便で運ぶか）はまだどこにも無い**（2026/09/13 落合さん確認）。
  決まったら日の見出しの横に足す。

#### アームの月別出荷（実績・推移タブ）

年度はじめ（4月）からの月別台数。こちらは**JSONでは足りない**
（スナップショットは今日から31日ぶんしか入っていない）ので、
元の .xlsm の `出荷明細` シートを直接読む。

- `harvestArmMonthly()` … 元ファイルが変わったときだけ集計する。
  変わっていなければフォルダを見るだけで終わる（毎晩 `harvestDailyData` から）。
  変換は数十秒かかるので、残り90秒を切っていたら次回にまわす。
  すぐ集計したいときは `アームの出荷実績を集める()`。
- 結果は出荷実績の蓄積スプレッドシートの `アーム日次` シートに
  `日付 / 区分 / 台数` で貯める（毎回まるごと入れ替え）。
  **月でまとめずに日で貯めるのが要点。** 集計し直すのは元ファイルが変わった
  ときだけ（週1回程度）なので、月で持つと「今月の途中まで」が作れず、
  今月の棒に先の予定まで混ざってしまう。読むときに今日で切る。
- **この表は実績。今日より後は出さない**（今月は途中まで／来月以降は出さない）。
  画面にも「実績のみ（9/13まで）」と書いてある。
  アームタブのKPIも同じ実績を使う（`9月 出荷（13日まで）` / `9月 うち 13ton`）。
  月の途中なので「◯日まで」を必ず添える。添えないと月まるごとの数と
  読み違える。
- KPIの `9月 予定こみ 合計`（`currentAll`）だけは**今日で切らない**。
  今月あと何台出るのかを知りたいため。実績との差が「これから出る台数」。
- 区分は機器の欄の先頭（全角スペースの前）。`13ton仕上げ` `13ton ｼｮｰﾄ` は
  まとめて `13ton`。ブームブラケットは除く（PDF生成側と同じ）。
- 容器は「本」、アームは「台」なので、同じグラフには混ぜない。

### グラフの数字の出し方（2026/09/16）

「数字が見にくい」と言われて直した。原因は2つ。

1. 字が小さかった（8〜8.5px）→ 棒や線の上の数字は **10px**、目盛りと月名は9〜10px。
2. **縁取り（`paint-order:stroke`）では線を隠しきれない。** 縁取りは字の形に沿うので、
   字と字のすき間を通った線がそのまま見える。実際、在庫の折れ線が
   「7,435」の真ん中を横切っていた。
   → `VizNum` を作り、**面色の下敷き（rect）を1枚敷いてから字を置く**ようにした。

`tools/chart_test.js` が実ブラウザで描いて、字の大きさ・重なり・下敷きの有無を数える。
グラフに数字を足すときは `VizNum` を使うこと。

### 生産の流れ（2026/09/17）

野外置場タブの一番上。当日作った容器を登録して、
**未受検 → 受検済 → 入庫済 → 出荷済** を追う。`gas/noda_prod_lot.js`。

| 状態 | 誰が動かすか |
| --- | --- |
| 未受検 | 生産を登録した時点 |
| 受検済 | 画面で「受検OK」 |
| 入庫済 | 画面で「入庫する」→ 置場を選ぶ。**置場の実績数に自動で足す** |
| 出荷済 | **人は押さない。** 指図書の容器Noと突き合わせて自動で引く |

守っていること：

- **本数は容器番号から数える**（`54401〜54480` → 80本）。人に数えさせるとずれる。
- **機種は機種マスタから選ぶ。** 品名とサイズはマスタから引く（手打ちさせない）。
  マスタに無いコードは登録できない。
- **番号の重なりを弾く。** 同じ容器を二重に登録すると在庫が二重になる。
- **二重に引かない。** 照合は毎晩走るので、ロットごとに「もう何本引いたか」
  (`出荷済本数`) を持ち、前回からの差ぶんだけ置場から引く。何度走らせても同じ結果。
- **部分出荷を扱う。** 100本のうち30本だけ指図書に載ることがある。
  重なったぶんだけ引き、全部出たら `出荷済` にする。
- **置場の増減は `yardUpdateLocation()` を通す。** 置場容量シートが正で、
  変更履歴にも残る。このシートは在庫数を持たない（2か所で持つと必ず食い違う）。
- 照合には指図書の容器Noレンジが要る。`shipact_index_()` に `ranges` を足した
  （`byOrder` は依頼Noで1件にまとめるので、枝番が複数ある指図書のレンジが落ちる）。

`tools/prodlot_test.js` が二重引き・部分出荷・重複指図書・マイナス防止を押さえている。

### 野外置場タブを作り直した（2026/09/17）

もとは別プロジェクト（2021年のアプリ）を **iframe で埋め込んで**いた。
中身は使えるが見た目も操作も他のタブと違い、入れ子のスクロールで
iPhoneでは扱いづらかった（落合さんの指摘）。
**一覧・編集・履歴・推移はアプリ側で作り直し、埋め込みはやめた。**

| やること | どこ |
| --- | --- |
| 置場の一覧・検索・本数を直す | `YardCapacityTab`（React）＋ `gas/noda_yard_tab.js` |
| 変更履歴（誰がいつ直したか） | `getYardChangeLog()` →「変更履歴」シート |
| 在庫の推移（日次） | `getYardDailyTotals()` →「日次在庫」シート |
| 敷地レイアウト図・建屋の編集 | **作り直していない。** 元のアプリをリンクで開く（`?page=yard`） |

守っていること：

- **数字の置き場所は変えていない。** 読み書きは今までと同じ「置場容量」シート。
- **保存は元アプリと同じ `yardUpdateLocation()` を通す。** 変更履歴の残り方を
  2通りにしないため（自前で書くと履歴の形が食い違う）。
- **使用率はサイズごとに出す。** 合計で割ると、20kgしか置かない場所に
  50kgのMAXが混ざって実態と合わない。収容0のサイズは出さない（0÷0を出さない）。
- 一覧にキャッシュは付けない。直した直後に古い数字が出ると、直したつもりが
  直っていないように見えて一番困る。
- タブを開いたときに取る（起動時には取らない）。3回呼ぶので最初の表示が遅くなる。
- 推移は「変更履歴」からは作れない（文字なので）。`harvestYardDailyTotals()` が
  1日1行の合計を「日次在庫」に貯める（夜間の取込から。同じ日に何度呼んでも1行）。
  すぐ始めたいときは `野外置場の今日ぶんを記録する()`。

## 開発の流れ

```bash
clasp pull                 # 本番の現状を取得（作業前に必ず実行して差分を確認）
# gas/ 配下を編集
clasp push                 # 本番プロジェクトのコードを更新（Webアプリはまだ変わらない）
clasp deployments          # デプロイ一覧
clasp redeploy <deployId>  # アクティブなデプロイを新バージョンに更新（Webアプリに反映される）
```

`.jsx` を編集した場合は、HANDOFF.md の手順でコンパイル済みHTMLを作り直してから
`gas/noda_dashboard.html` を差し替える（`.jsx`だけ変更してもWebアプリには反映されない）。
